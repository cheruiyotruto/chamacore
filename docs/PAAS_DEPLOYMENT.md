# PaaS deployment (Render / Railway / Fly.io)

This repository now contains ready-to-use deployment configs for all three
platforms. Pick **one** — they describe the same application, not a shared
stack.

| File | Platform |
|---|---|
| `render.yaml` | Render Blueprint |
| `.railway/railway.ts` | Railway Infrastructure as Code |
| `fly.toml` | Fly.io |

All three build the **last stage** of `Dockerfile`, named `paas`. That stage
runs PHP-FPM and nginx in a single container, listens on `$PORT`, and reuses
the same image for the queue worker and scheduler. The original `runtime` and
`web` stages used by `docker-compose.yml` are unchanged.

## Important: MySQL vs Postgres

The app's migrations use a few MySQL-only `->after()` modifiers. Laravel
silently ignores them on Postgres, so a fresh Postgres install works, but the
project's own `docs/DEPLOYMENT.md` still targets MySQL. All three PaaS configs
therefore use **Postgres**, which is the managed relational database each
platform actually offers. Test the migration on a staging database first.

## 1. Before you start

1. **A Git repository with a remote.** This folder is not currently a Git
   repo. From the project root:

   ```bash
   git init
   git add .
   git commit -m "Prepare Chama Core for PaaS deployment"
   git remote add origin https://github.com/YOUR_ACCOUNT/chama-core.git
   git push -u origin main
   ```

   Confirm `.env`, `vendor/`, `node_modules/` and `storage/logs/*` are ignored
   before committing.

2. **A fresh application key.** Generate one locally:

   ```bash
   php artisan key:generate --show
   ```

   or without PHP:

   ```bash
   echo "base64:$(openssl rand -base64 32)"
   ```

3. **A strong platform admin password.** The seeder creates the first super
   admin on the first deploy. Use `.env.paas.example` as the checklist for all
   values you must supply.

4. **Never set `CHAMA_SEED_DEMO=true` in production.** All configs set it to
   `false`.

5. **Custom domain (optional).** Each platform gives you a free `*.onrender.com`
   / `*.railway.app` / `*.fly.dev` hostname. If you use your own domain, set
   `APP_URL` to the final HTTPS URL and `SANCTUM_STATEFUL_DOMAINS` to the bare
   hostname.

### Shared variables (set these on every platform)

| Variable | Value |
|---|---|
| `APP_KEY` | the fresh key from step 2 |
| `APP_URL` | `https://<your-hostname>` |
| `SANCTUM_STATEFUL_DOMAINS` | `<your-hostname>` |
| `PLATFORM_ADMIN_EMAIL` | your admin email |
| `PLATFORM_ADMIN_PASSWORD` | a long random password |
| `DB_URL` | the managed Postgres connection string (wired automatically on Render/Railway; set as a Fly secret) |

### Payment/payout webhook secrets (required)

Payment and payout callbacks are rejected with HTTP 503 when the matching
secret is empty in production. Set all three even if you only use M-Pesa today:

| Variable | Used by |
|---|---|
| `MPESA_CALLBACK_SECRET` | STK push callbacks (`/api/v1/payments/mpesa/callback`) |
| `MPESA_B2B_CALLBACK_SECRET` | M-Pesa B2B payout results |
| `BANK_PAYOUT_CALLBACK_SECRET` | Bank payout webhooks |

Daraja cannot send custom headers, so append the secret to the registered
callback URL, e.g.
`https://your-host/api/v1/payments/mpesa/callback?callback_secret=<secret>`.
Gateways that can set headers may instead send `X-Callback-Secret` or
`X-Callback-Signature` (HMAC-SHA256 of the raw body). Use a different long
random value for each secret.

The app also refuses to boot in production with `APP_DEBUG=true`, a placeholder
`APP_KEY`, or `CHAMA_SEED_DEMO=true`. `HSTS_PRELOAD` defaults to `true`; set it
to `false` only if some subdomain is not HTTPS-ready.

## 2. Render

1. Push the repo to GitHub/GitLab.
2. In Render, click **New + → Blueprint**.
3. Connect the repository and select the branch (`main`).
4. Render reads `render.yaml` and shows: Postgres, web service, queue worker,
   scheduler.
5. Fill the prompted values: `APP_URL`, `SANCTUM_STATEFUL_DOMAINS`,
   `PLATFORM_ADMIN_EMAIL`, `PLATFORM_ADMIN_PASSWORD`. `APP_KEY` is generated by
   Render automatically.
6. Choose the region, then **Apply**.
7. Wait for all services to become **Live**. The web service runs migrations,
   seeds the admin, optimizes Laravel and then starts nginx on first boot.
8. Open `https://<service>.onrender.com/up` — it should return `OK`.
9. Log in at `/login` with the `PLATFORM_ADMIN_*` credentials.

Notes:
- The 5 GB Render disk is mounted at `/var/www/html/storage` so uploads survive
  redeploys. It belongs to the web service only; worker-generated files are
  ephemeral. Move to S3 if workers must share files.
- Free Postgres is not suitable for real data. Use at least the `0.5c-1g` plan
  included in the blueprint.
- To deploy updates, just push to `main`.

## 3. Railway

Railway deprecated service-level `railway.json`; this repo uses the newer
`.railway/railway.ts` Infrastructure as Code file.

1. Push the repo to GitHub.
2. Install the SDK and log in:

   ```bash
   npm install railway
   npx railway login
   npx railway link          # select/create your project and environment
   ```

3. Preview the changes:

   ```bash
   npx railway config plan
   ```

4. Apply:

   ```bash
   npx railway config apply
   ```

   This creates the Postgres database, 5 GB volume, and the `web`, `worker`
   and `scheduler` services. Railway detects the `Dockerfile` automatically.
5. In the Railway dashboard, open the **web** service → **Variables** and set
   the shared variables from section 1 (`APP_KEY`, `APP_URL`,
   `SANCTUM_STATEFUL_DOMAINS`, `PLATFORM_ADMIN_EMAIL`,
   `PLATFORM_ADMIN_PASSWORD`), plus the three webhook secrets from the table
   above. The config uses `preserve()` for these so Railway will not overwrite
   your values on the next apply. `APP_KEY` and `APP_URL` are propagated to the
   `worker` and `scheduler` services automatically so queued jobs generate
   correct links — only set them on **web**.
6. The web service's pre-deploy command runs `migrate`, `db:seed` and
   `optimize` on every deploy. Watch **Deployments → Logs** for errors.
7. Open the generated domain + `/up`, then log in at `/login`.
8. Generate a public domain under the web service → **Settings → Networking**
   if you need a stable URL.

Note: a Railway volume can only be attached to one service, so it is mounted
on `web` only. Same storage caveat as Render.

## 4. Fly.io

1. Install the [flyctl CLI](https://fly.io/docs/hands-on/install-flyctl/) and
   log in: `fly auth login`.
2. Edit `fly.toml`: change `app = "chama-core"` to a globally unique name and
   set `primary_region` to the region nearest your users.
3. Launch (this creates the app and asks about Postgres):

   ```bash
   fly launch --no-deploy
   fly postgres create --name chama-core-db --region <same-region>
   fly postgres attach chama-core-db --app <your-app-name>
   ```

4. Set the secrets (the app reads `DB_URL`, not `DATABASE_URL`):

   ```bash
   fly secrets set \
     APP_KEY='base64:...' \
     APP_URL='https://<your-app>.fly.dev' \
     SANCTUM_STATEFUL_DOMAINS='<your-app>.fly.dev' \
     DB_URL='postgres://USER:PASSWORD@chama-core-db.flycast:5432/chama_core?sslmode=disable' \
     PLATFORM_ADMIN_EMAIL='owner@example.com' \
     PLATFORM_ADMIN_PASSWORD='a-long-random-password' \
     MPESA_CALLBACK_SECRET='a-long-random-secret' \
     MPESA_B2B_CALLBACK_SECRET='a-different-long-random-secret' \
     BANK_PAYOUT_CALLBACK_SECRET='another-different-long-random-secret'
   ```

   The three callback secrets are mandatory: payment and payout webhooks are
   rejected with HTTP 503 until they are set. Fly secrets apply to every
   process (`app`, `worker`, `scheduler`), so the workers can also send
   notifications that contain signed links.

   `fly postgres attach` prints the exact internal host, user and password to
   use in `DB_URL`. Internal `.flycast` traffic does not need TLS, hence
   `sslmode=disable`; the config's `DB_SSLMODE=require` is overridden by the
   query string.

5. Deploy:

   ```bash
   fly deploy
   ```

   The `release_command` runs migrations/seed/optimize once before the three
   processes (`app`, `worker`, `scheduler`) start.
6. Check status with `fly status` and `fly logs`, then open
   `https://<your-app>.fly.dev/up`.

Note: Fly volumes are per-machine, so `fly.toml` intentionally does not mount
one. Uploads are ephemeral until you add a volume per machine or switch to
S3-compatible storage. For a money-handling system, configure S3 before going
live.

## 5. Post-deploy verification (all platforms)

```bash
# In the platform's shell/console for the web service:
php artisan about
php artisan chama:reconcile-ledgers --strict
php artisan schedule:list
php artisan queue:failed
```

Also confirm: `/up` returns `OK`, `/` loads the white/gray marketing site,
`/login` works, and the demo tenant is absent.

## 6. Updates and rollback

- Push to the connected branch (or `fly deploy`). The web service re-runs
  `migrate --force`, `db:seed --force` and `optimize` on each release; both
  seeders are idempotent.
- Back up the Postgres database and `APP_KEY` before every release. Without
  the same `APP_KEY`, encrypted fields and sessions cannot be recovered.
- Roll back by redeploying the previous commit/image together with its DB
  backup.
